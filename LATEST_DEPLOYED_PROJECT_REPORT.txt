1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
perfect-foundation-sms is a multi-tenant School Management System (ERP) built
for a franchise model: a holding company operates many schools, each school owns
multiple campuses, and users belong to a school while being scoped to one or more
campuses. Identity, role-based access control (RBAC), multi-tenancy and campus
isolation are the most mature parts of the codebase. Finance, HR/payroll,
operations and reporting are partially built.

STATUS (as of latest deployment): the application is LIVE on Vercel with a Neon
PostgreSQL production database. All 34 modules are populated with real demo data,
47 of 48 frontend routes render without errors, and two genuine production defects
(payroll end-to-end and the inquiry-list 500) were found, fixed, deployed and
verified this session. The foundation (authentication + isolation + data model)
is the strongest area; frontend feature depth remains ~35%.

5.1 CONFIGURATION
   config.settings.base holds the whole configuration: installed apps (18+
   library apps plus 33 local apps), the middleware chain, DRF authentication
   (JWT + session), default throttles, custom exception handling, templates/media
   and database selection. The database is resolved from DATABASE_URL, else
   standard Postgres env variables, with development falling back to SQLite.
   config.settings.test runs on in-memory SQLite with MD5 password hashing for
   speed. Production settings load DATABASE_URL / DJANGO_SECRET_KEY from the
   environment (Vercel).

5.4 CROSS-CUTTING MECHANISMS
   - Authentication: Custom EmailOrUsernameBackend; DRF JWT + session; lockout,
     2FA, password history.
   - RBAC: 15 roles; granular 3-part permission codenames (app.resource.action).
   - Multi-tenancy: ActiveInstitutionMiddleware + CampusAccessMiddleware +
     TenantManager/CampusScopedManager + access.py helpers enforce tenant/campus
     isolation.
   - Module gating: ModuleAccessMiddleware 403s requests to disabled modules.
   - Admin: Django Admin at /admin/, protected media serving, audit logging.

5.5 DATA MODEL HIGHLIGHTS
   - Tenant spine: School -> Campus -> AcademicUnit -> Class -> Section;
     SubjectOffering links subject + class + year.
   - Finance: Invoice, Payment, Expense + journal, FeeStructure/FeeCategory,
     PDF receipt generation.
   - People: User (custom), Student + StudentGuardianLink, Teacher,
     StaffProfile/Employee.
   - IDs / documents: DigitalId in digital_ids module; ReportLab-driven
     receipts & report cards.

7. PRODUCTION BUG FIXES DEPLOYED
--------------------------------------------------------------------------------
7.1 PAYROLL END-TO-END FIX  (commit 2d7f1a1)
   Problem:
     - Serializers referenced a stale "teacher" relationship instead of "employee".
     - The payroll DB schema had teacher_id non-nullable, blocking writes.
     - PayslipListView used the wrong kwarg path (teacher_path vs employee_path).
   Fix:
     - Corrected serializers/views to use "employee"; aligned the schema;
       reseeded payroll fully.
   Result:
     - Payroll works end-to-end and returns real data on the live API:
       146 salary structures, 438 payroll records, 438 payslips (3 pay periods).
   Files:
     - backend/apps/payroll/serializers.py, backend/apps/payroll/views.py.

7.2 INQUIRY LIST 500 FIX  (commit 55216f1)
   Problem:
     - InquiryListCreateView.get_queryset (backend/apps/students/views.py:863)
       called select_related("guardian", ...) but the Inquiry model has NO
       "guardian" FK -- it only has string fields guardian_name/guardian_email.
     - This raised FieldError -> HTTP 500 on /api/students/inquiries/.
   Fix:
     - Removed the stale "guardian" select_related reference.
   Result:
     - The endpoint now returns 200 with real content.
   Files:
     - backend/apps/students/views.py

8.2 DEMO DATA SEEDER DESIGN
   The accounts.demo_seed package provides a five-part, idempotent, tenant-
   isolated seeding command:
       python manage.py seed_demo_data [--part=1..5 | --all]
   Every record is created strictly for the Demo Education Group school
   (DEMO-EDU, id=3) with five campuses and enforced campus isolation. The command
   is safe to re-run (idempotent), uses a single dev password of
   DemoPassword!2026, and never touches pre-existing tenants.

   Seed parts at a glance:
     1 - Foundation   : School, campuses, academic years, roles, permissions,
                        base users               -> 3 years, 5 campuses
     2 - Academics    : Classes, subjects, teachers, support staff, parents,
                        students                 -> 500 students, 350 guardians,
                                                    50 teachers, 65 classes,
                                                    195 sections
     3 - Operations   : Attendance, leaves, exams, results, fee structures,
                        invoices, payments, accounting
     4 - Assets/HR    : HR, payroll, library, transport, inventory, fixed assets
     5 - Integration  : LMS, homework, discipline, events, comms, helpdesk,

9.2 ROOT CAUSES OF FAILURES
   (a) Rate limiting (throttling) inside tests - most common cause. Auth views
       set explicit throttle scopes (login, password_reset); the test settings
       only clear DEFAULT_THROTTLE_CLASSES, so scoped throttles still fire and
       tests get HTTP 429 ("Request was throttled"). Affects accounts
       login/lockout/session tests and several school isolation setUpClass blocks.
   (b) Test-file defects (not product code):
       - apps/students/tests.py uses APIClient but never imports it.
       - apps/finance/tests.py uses APIRequestFactory which is shadowed/
         unavailable in a shared context.
       - Some tests expect the old 2-part permission codename (resource.action)
         while code now emits 3-part (app.resource.action).
       - Tests expect student.age and a plaintext receipt code that the API no
         longer exposes (behavior change not propagated to tests).
   (c) Genuine code defects surfaced by the run - see the Severity Matrix
       (Section 11).

   NOTE ON SCOPE: All failures/errors above are pre-existing and unrelated to the
   demo-data seeder work. The seeder changes are confined to accounts/demo_seed/*
   and seed_demo_data.py; no test module imports or exercises that code (verified
   by grep across all test files).
