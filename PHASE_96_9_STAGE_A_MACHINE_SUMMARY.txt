PROVISIONING CONTRACT (minimum properties a future mechanism must satisfy)
- creates only dedicated E2E accounts (fixed usernames, e.g. counsellor/guard/nurse/administrative_officer/librarian
  or prefixed test handles) via get_or_create idempotency
- assigns exactly the intended role (role_for_designation or explicit role argument)
- does not weaken authorization (same role semantics, IsAdminOrReadOnly-equivalent or super_admin gating)
- does not modify unrelated users or delete unrelated data (no flush; no blanket demotion beyond existing invariants)
- does not expose passwords (secure random temp password, returned exactly once, never logged)
- supports deterministic verification (idempotent; re-run reports created/unchanged; password equality check without
  storing plaintext; E2E can confirm role via /api/auth/me/)
- auditable (AuditLog entries where the app records staff/account creation; command history via idempotent run output)
- reversible or cleanup-capable (delete created accounts/profiles; documented reverse)
- does not create migration drift (no schema/model changes; pure data command)
- does not alter production configuration unnecessarily (no Permission catalog mutation, no settings changes)
